### P3 fix — les 3 bugs POS/offline/PO corrigés et appliqués en live

Trois nouvelles migrations, chacune testée dans une transaction `BEGIN`/`ROLLBACK` (avec simulation de `auth.uid()` via `set_config('request.jwt.claims', ...)` pour exercer les fonctions `SECURITY DEFINER` réalistement) avant application, puis appliquées en live et vérifiées.

**1. `20260723120000_fix_customer_credit_upsert_by_phone.sql`** — le bug documenté en P3 (RPC hors-ligne `increment_customer_credit` appelée avec des paramètres qui ne correspondent à aucune fonction déployée) s'est révélé plus large en creusant : **le chemin EN LIGNE était lui aussi cassé**. Vérifié en base live (`pg_constraint`) : aucune contrainte UNIQUE n'existe sur `customers(organization_id, phone)`, alors que le code en ligne fait `.upsert(data, { onConflict: "phone,organization_id" })` — Postgres exige une contrainte UNIQUE réelle correspondante, sinon erreur 42P10, avalée silencieusement par le code (`if (!custErr && ...)`). Résultat : un client réglant à crédit pour la première fois via son téléphone ne voyait jamais son crédit enregistré, en ligne comme hors-ligne. Vérifié : 0 doublon `(organization_id, phone)` existant, ajout de la contrainte sûr. Nouvelle RPC atomique `increment_customer_credit_by_phone` (find-or-create client + incrément crédit + trace `customer_credits`) remplace l'ancien enchaînement fragile en 3 appels ; `useOfflineSale.ts` mis à jour pour les deux chemins (en ligne et hors-ligne).

**2. `20260723130000_fix_sale_idempotency.sql`** — contrainte UNIQUE ajoutée sur `sales(organization_id, sale_number)` (0 doublon existant, vérifié) + `create_full_sale` vérifie désormais l'existence d'une vente avec ce `sale_number` AVANT d'insérer (et retombe sur l'id existant en cas de conflit concurrent) : un replay de mutation offline après perte de la réponse serveur devient un no-op réussi plutôt qu'une vente en double avec double décrément de stock. Testé explicitement : deux appels avec le même `sale_number` → une seule vente créée.

**3. `20260723140000_fix_receive_purchase_order_partial.sql`** — `purchase_order_items.quantity_received` est désormais persisté par ligne (cumulatif, plusieurs réceptions possibles) et `purchase_orders.status` ne passe à `'received'` que si toutes les lignes sont entièrement reçues, sinon `'partial'`. Testé explicitement : réception de 4 puis 6 sur une commande de 10 → `quantity_received=10`, `status='received'` après la seconde réception, `status='partial'` après la première.

Validation post-application complète : `npm run typecheck` (0 erreur), `npm run lint` (0 erreur), `npm run build` (succès), `npm test -- --run` (81/81 fichiers, 1065/1065 tests — 6 nouveaux tests apparus car `checkPlanLimitJsonbPattern.test.ts` scanne dynamiquement la dernière migration touchant `create_full_sale` ; allowlist mise à jour avec la nouvelle migration), `validate_sql_migrations.py` et `check_undefined_functions.py` (0 erreur).

### P4 — Audit sécurité RLS (2026-07-24)

Après le fix du bug remonté par l'utilisateur, reprise du plan à P4. Méthode : lister toutes les policies RLS référençant `has_role()` (`pg_policies`), analyser chacune pour une comparaison manquante entre l'appelant et la ligne ciblée, puis **vérifier en live** chaque hypothèse via une transaction `BEGIN`/`ROLLBACK` simulant un vrai admin (`set_config('request.jwt.claims', ...)` + `SET LOCAL ROLE authenticated`) ciblant une organisation distincte de la sienne — jamais Diallo & Frères (RULE 1). Chaque fix a été rejoué dans une transaction avant application live, puis appliqué et re-vérifié.

**1. `organizations` (UPDATE, `admin_can_update_org`)** — la policy autorisait via `has_role(auth.uid(),'admin')` sans comparer avec `id` de la ligne ciblée. Sur le papier : n'importe quel admin pouvait modifier n'importe quelle organisation. **Test live contre-intuitif** : un admin réel de l'org A ciblant une org B réelle a vu son UPDATE affecter **0 ligne**, alors qu'une requête de contrôle dans le même contexte confirmait `has_role(...) = true`. Cause : Postgres exige qu'une ligne soit visible via une policy SELECT applicable pour évaluer la clause WHERE d'un UPDATE — la policy SELECT `members_can_view_org` (scopée par `is_member_of_organization`) rendait la ligne invisible pour cet admin, neutralisant la faille UPDATE en pratique, mais par effet de bord non voulu. Corrigé quand même en profondeur (`20260724100000_fix_organizations_update_cross_tenant.sql`) : la policy UPDATE doit être correcte par elle-même, indépendamment du hasard d'une autre policy.

**2. `password_reset_tokens` (INSERT/UPDATE)** — aucune condition `organization_id`, contrairement à la policy SELECT qui, elle, laisse passer les lignes `organization_id IS NULL` pour tout admin. Table vide en prod (aucune fuite réelle), mais lue directement par le client (`ResetTokensPanel.tsx`) donc exposée à PostgREST. Les deux Edge Functions qui écrivent sur cette table utilisent le `service_role` (contourne RLS) — fix sans impact applicatif. Corrigé (`20260724110000_fix_password_reset_tokens_org_scope.sql`).

**3. `user_roles` (SELECT, `user_roles_select_scoped`)** — **fuite inter-tenant réelle et déjà exploitable via l'UI existante**, pas seulement théorique : `Users.tsx` interroge `supabase.from("user_roles").select("user_id, role, created_at")` sans filtre, en s'appuyant entièrement sur RLS. La policy live laissait passer les lignes de **toutes** les organisations pour tout admin (hors `super_admin`) — la réponse réseau brute contenait déjà les `(user_id, role)` de tous les clients de la plateforme, même si l'affichage final les filtrait ensuite via la jointure `profiles` (elle, correctement scopée). Fix non trivial : un `EXISTS(SELECT ... FROM profiles ...)` direct dans la policy provoque une récursion infinie (`42P17`), car `profiles_select_scoped` interroge elle-même `user_roles`. Résolu via une nouvelle fonction `SECURITY DEFINER get_organization_id_of_user()` (même mécanisme que `get_user_organization_id()`), qui contourne RLS et casse le cycle (`20260724120000_fix_user_roles_select_org_scope.sql`).

**4. `user_audit_log` (INSERT, `admins_insert_audit_log`)** — aucune contrainte sur `actor_id` : un admin pouvait forger une entrée attribuée à l'admin d'une autre organisation (falsification du journal d'audit). Le seul appel client légitime (`AuditLogPanel.tsx`) utilise toujours `actor_id: userData.user?.id` — fix (`actor_id = auth.uid()` obligatoire) sans impact (`20260724130000_fix_user_audit_log_insert_forgery.sql`).

**5. `stripe_events` — CRITIQUE, RLS entièrement désactivée en live.** Découvert en vérifiant les tables sans RLS (`pg_class.relrowsecurity`) : une seule table sur tout le schéma, `stripe_events`. La migration `20260705060000_force_row_level_security.sql` y appliquait déjà `FORCE ROW LEVEL SECURITY` — sans effet, car `FORCE` exige que `ENABLE ROW LEVEL SECURITY` ait déjà été exécuté, ce qui n'a jamais été le cas. De plus, `authenticated` avait des GRANT bruts SELECT/INSERT/UPDATE/DELETE hérités du schéma initial. Conséquence : **n'importe quel utilisateur authentifié, tout rôle et toute organisation confondus** (y compris un simple vendeur), pouvait lire l'intégralité des événements Stripe de toutes les organisations (payload JSON complet — ids clients Stripe, abonnements, factures) ou en forger. Vérifié : table vide (0 ligne, aucune fuite réelle constatée), et aucun code applicatif actuel ne touche cette table Postgres (le webhook `stripe-webhook` utilise Deno KV pour l'idempotence, pas cette table) — fix sans risque de régression. Corrigé en alignant sur l'intention déjà documentée mais jamais appliquée dans `20260708000000_p1_security_fixes.sql` : `ENABLE`+`FORCE ROW LEVEL SECURITY`, policy `service_role` (ALL), policy `authenticated` (SELECT scopé par organisation), REVOKE des droits d'écriture bruts (`20260724140000_fix_stripe_events_rls_disabled.sql`).

**Vérification complémentaire** : les droits DELETE/TRUNCATE accordés à `authenticated` sur la quasi-totalité des autres tables du schéma sont le comportement par défaut standard de Supabase (DELETE reste filtré par RLS ; TRUNCATE n'est de toute façon pas exposable via l'API REST de PostgREST) — traité comme recommandation de durcissement pour une passe P5 ultérieure, pas comme un bug à corriger immédiatement (RULE 0 : pas de changement non nécessaire).
